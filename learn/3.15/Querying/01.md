# Querying basics

* https://prometheus.io/docs/prometheus/latest/querying/basics/

Prometheus provides a functional query language called PromQL (Prometheus Query Language) that lets the user select and aggregate time series data in real time.

When you send a query request to Prometheus, it can be an *instant query*, evaluated at one point in time, or a *range query* at equally-spaced steps between a start and an end time. PromQL works exactly the same in each case; the range query is just like an instant query run multiple times at different timestamps.

In the Prometheus UI, the "Table" tab is for instant queries and the "Graph" tab is for range queries.

Other programs can fetch the result of a PromQL expression via the [HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/).

## Examples[](https://prometheus.io/docs/prometheus/latest/querying/basics/#examples)

This document is a Prometheus basic language reference. For learning, it may be easier to start with a couple of [examples](https://prometheus.io/docs/prometheus/latest/querying/examples/).

## Samples[](https://prometheus.io/docs/prometheus/latest/querying/basics/#samples)

The value of a sample at a given timestamp returned by PromQL may be a float or a [native histogram](https://prometheus.io/docs/specs/native_histograms/). A float sample is a simple floating point number, whereas a native histograms sample contains a full histogram including count, sum, and buckets.

Note that the term "histogram sample" in the PromQL documentation always refers to a native histogram. The term "classic histogram" refers to a set of time series containing float samples with the `_bucket`, `_count`, and `_sum` suffixes that together describe a histogram. From the perspective of PromQL, these contain just float samples, there are no "classic histogram samples".

Both float samples and histogram samples can have a counter or a gauge "flavor". Float samples with a counter or gauge flavor are generally simply called "counters" or "gauges", respectively, while their histogram counterparts are called "counter histograms" or "gauge histograms". Float samples do not store their flavor, leaving it to the user to take their flavor into account when writing PromQL queries. (By convention, time series containing float counters have a name ending on `_total` to help with the distinction.)

Since histogram samples "know" their counter or gauge flavor, this allows reliable warnings about mismatched operations. For example, applying the `rate` function to gauge floats will most likely produce a nonsensical result, but the query will be processed without complains. However, if applied to gauge histograms, the result of the query will be annotated with a warning.

>
> 样本(Samples)
> PromQL 返回的在给定时间戳下的样本值, 可以是一个浮点数(Float), 也可以是一个原生直方图(Native Histogram). 浮点样本就是一个简单的浮点数值; 而原生直方图样本则包含了一个完整的直方图(包括 count、sum 和 buckets 数据).

>
> 浮点样本和直方图样本都可以具有 Counter(计数器) 或 Gauge(测量值) 的"风味(Flavor, 即语义属性)". 具有 Counter 或 Gauge 属性的浮点样本, 通常简称为"Counters"或"Gauges"; 而对应的直方图样本则分别称为"Counter 直方图(counter histograms)"或"Gauge 直方图(gauge histograms)". 浮点样本本身并不存储其类型属性, 这就需要用户在编写 PromQL 查询时自行考虑其类型(按照业界惯例, 包含浮点计数器的时间序列名称通常以 `_total` 结尾, 以便于区分).
>
> 由于原生直方图样本能够"知道"自身是 Counter 还是 Gauge 属性, 这使得系统能够在操作不匹配时发出可靠的警告. 例如, 对 Gauge 类型的浮点数应用 `rate()` 函数很可能会产生荒谬无意义的结果, 但查询引擎仍会毫无怨言地执行处理; 然而, 如果将 `rate()` 应用于 Gauge 类型的直方图, 查询结果中就会附带一条警告注解.

### 二、核心内容总结

这段文档主要阐述了以下 3 个维度的核心概念:

1. PromQL 的两种执行模式: 即时查询(Instant Query)与区间查询(Range Query)在引擎底层的评估机制完全相同, 区间查询就是即时查询的时间切片重复.
2. PromQL 内部的数据样本形态: 区分了标量浮点样本(Float)与原生直方图(Native Histogram). 明确指出了"经典直方图"在引擎眼里只是分散的普通浮点数, 而"原生直方图"是一个自包含的复合对象.
3. 样本类型的感知能力与安全性: 浮点样本没有类型元数据(无状态/无感知), 类型正确性全靠人肉把控(通过命名规范如 `_total` 规避); 而原生直方图具备类型感知(Type Awareness), 能对错误操作(如对 Gauge 调用 `rate()`)做出智能告警.

   在浮点时代, Prometheus 引擎底层不知道一个数字是 Counter 还是 Gauge. 如果你手抖对 `node_memory_MemFree_bytes`(Gauge)套了一层 `rate()`, Prometheus 会正常给你算出一个极其荒谬的数字, 既不报错也不警告. 官方在这里是在推介原生直方图带来的巨大改进 -- 它自带元数据, 引擎终于能做"静态/动态语义检查"了.

### 问题 1: 什么是直方图? 请用具体数据示例说明绘制步骤

#### 什么是直方图?

直方图(Histogram)是一种用来展示数据分布情况的统计图表.
在监控场景中, 普通的"平均值"常常会掩盖真相(例如: 99% 的请求只要 10ms, 但 1% 的请求要 10s, 平均值会被拉高, 但你看不出到底是全变慢了还是长尾延迟). 直方图通过把数据切分成若干个连续的"区间/桶(Buckets)", 并统计每个区间内落入的数据数量, 从而清晰展现数据的离散和分布特征.

#### 真实数据示例

假设我们要统计某个接口在 1 分钟内的 10 次 HTTP 请求耗时(单位: 毫秒 ms), 原始数据如下:

> `[12, 18, 45, 60, 85, 120, 150, 190, 310, 420]`
>

#### 绘制一个直方图的具体步骤:

* 步骤 1: 确定极值与数据范围(Range)
  * 最小值(Min) = 12ms, 最大值(Max) = 420ms.
  * 总范围跨度 = 420 - 12 = 408ms.

* 步骤 2: 划分区间桶(Buckets / Bins)
  通常根据经验或固定步长划分. 为了直观, 我们以 100ms 为步长, 将区间划分为 5 个连续的"桶"(采用左闭右开 `[a, b)` 原则):
  * 桶 1: `[0, 100)`
  * 桶 2: `[100, 200)`
  * 桶 3: `[200, 300)`
  * 桶 4: `[300, 400)`
  * 桶 5: `[400, 500)`

* 步骤 3: 统计每个区间的频数(Count / Frequency)
  将 10 个数据分别归类投递到桶中:
  * `[0, 100)`: 包含 12, 18, 45, 60, 85 $\rightarrow$ 共 5 次
  * `[100, 200)`: 包含 120, 150, 190 $\rightarrow$ 共 3 次
  * `[200, 300)`: 无 $\rightarrow$ 共 0 次
  * `[300, 400)`: 包含 310 $\rightarrow$ 共 1 次
  * `[400, 500)`: 包含 420 $\rightarrow$ 共 1 次

* 步骤 4: 绘制直方图图形
  * X 轴(横轴): 连续的时间区间(桶边界);
  * Y 轴(纵轴): 频数(落入区间的请求个数).

ASCII 图形化展示如下:

```bash
 频数 (请求次数)
  ▲
5 ┤  ┌─────┐
4 ┤  │     │
3 ┤  │     │  ┌─────┐
2 ┤  │     │  │     │
1 ┤  │     │  │     │         ┌─────┐  ┌─────┐
0 ┼──┴─────┴──┴─────┴──┴───┴──┴─────┴──┴─────┴──► 耗时 (ms)
    [0-100)  [100-200) [200-300) [300-400) [400-500)
```

### 问题 2: 什么是"经典直方图"与"原生直方图"?

在 Prometheus 体系中, 这两者的差异是存储架构上的一次重大飞跃.

#### 1. 经典直方图(Classic Histogram)

* 原理: Prometheus 早期在数据模型上不支持复杂结构体, 因此采用"拆骨架"的方式: 开发人员在客户端硬编码指定桶边界(比如 100ms, 200ms, 500ms), Prometheus 把一个直方图拆分成很多条独立的普通时间序列(全部是带特定后缀的 Float 浮点数).
* 特点: 桶是累计统计(Cumulative)的, 即 `le="200"` 包含了所有 $\le 200$ 的请求.

真实抓取(Scrape)示例:

```bash
# 经典直方图暴露出的是多条扁平化的普通浮点序列
http_request_duration_seconds_bucket{le="0.1"} 5     # <=100ms 有 5 次
http_request_duration_seconds_bucket{le="0.2"} 8     # <=200ms 有 8 次 (包含上面的 5 次)
http_request_duration_seconds_bucket{le="0.5"} 10    # <=500ms 有 10 次
http_request_duration_seconds_bucket{le="+Inf"} 10   # <=无穷大 有 10 次
http_request_duration_seconds_sum 1.392              # 总耗时累计
http_request_duration_seconds_count 10               # 总请求次数累计
```

* 缺点(痛点):
  1. 时间序列爆炸(Cardinality explosion): 如果你配置了 20 个桶, 再加上接口路径、状态码等维度, 一个指标就会膨胀出成千上万条时间序列, 极度消耗 Prometheus 内存.
  2. 精度与配置固化: 桶的区间在代码里写死了, 上线后如果想提高精度(比如细分 100ms 到 150ms), 必须改代码重发版; 算 P99 分位数时只能靠插值线性猜测.

---

#### 2. 原生直方图(Native Histogram, 又称高分辨率/稀疏直方图)

* 原理: Prometheus(v2.40 引入实验性支持, 并持续完善)在存储层直接支持了一种复合数据类型. 它不再把直方图拆分成几十个 `_bucket` 序列, 而是单条时间序列中的一个"样本(Sample)"本身就是一个完整的直方图对象.
* 特点: 它采用对数动态分桶(指数桶). 桶不需要用户手动硬编码, Prometheus 在内部自动稀疏存储, 精度非常高(可以动态划分几百上千个微小桶而几乎不占额外开销).

概念呈现示例(逻辑视角):
抓取端只暴露一条时间序列:

```bash
http_request_duration_seconds
```

当 Prometheus 在时间戳 `t` 抓取这个指标时, 存储下来的单个样本内部结构是这样的复合数据(以 JSON 伪代码描述):

```json
{
  "timestamp": 1715000000,
  "flavor": "counter",          // 自带类型信息: 它是个 counter 类型的直方图!
  "count": 10,                  // 观测总数
  "sum": 1.392,                 // 观测数值和
  "schema": 1,                  // 桶宽度划分模式(指数增长因子)
  "positive_buckets": {         // 动态生成的正数桶(只存非空的桶, 稀疏存储)
    "bucket[0.01 ~ 0.02]": 2,
    "bucket[0.04 ~ 0.05]": 1,
    "bucket[0.06 ~ 0.08]": 1,
    "bucket[0.08 ~ 0.10]": 1,
    "bucket[0.10 ~ 0.15]": 2,
    "bucket[0.15 ~ 0.20]": 1,
    "bucket[0.30 ~ 0.45]": 2
  }
}
```

#### 对比总结表:

| 特性 | 经典直方图 (Classic Histogram) | 原生直方图 (Native Histogram) |
| :--- | :--- | :--- |
| 在 TSDB 底层的表现 | 是一堆普通的浮点数序列 (`_bucket`, `_sum`, `_count`) | 是一条时间序列, 样本类型是复合 Histogram 对象 |
| 分桶方式 | 静态、硬编码桶边界(如 0.1, 0.2, 0.5) | 动态对数分桶, 自适应高分辨率(数百个桶) |
| 存储开销 | 序列基数极高, 容易造成 OOM | 序列基数极低, 稀疏存储, 大幅减少序列数 |
| 类型安全 | Prometheus 底层只看到 Float, 不知道你是个 Histogram | 自带 `Flavor`(标记了是 Counter 还是 Gauge), 能给 PromQL 提供警告检查 |

### 问题 3: 对于 Prometheus 中的指标, 指标值本身有哪些类型?

这里必须非常清晰地区分两个常被混淆的维度: "业务语义/客户端层面的类型" 与 "Prometheus 存储/PromQL 计算引擎层面的底层样本值类型".

#### 维度一: Prometheus 底层 TSDB 存储与 PromQL 样本值的真实类型(物理类型)

你在官方文档看到的内容指的就是这一层. 在 Prometheus 的底层引擎里, 一个时间戳对应的值(Sample Value)只有两种物理类型:

1. `Float64`(标量浮点型)
   * 这是绝大多数监控指标的物理值. 它就是一个单纯的 64 位双精度浮点数(如 `1.0`, `152.8`, `404`).
   * 特点: 它是无状态、无类型的"裸数据". 它不记录自己到底是个计数器还是内存大小, 引擎只管算数.

2. `Native Histogram`(原生直方图类型)
   * 这是为了解决经典直方图痛点引入的复合样本对象.
   * 特点: 一个 Sample 不再是一个单一的数字, 而是包含了 Count、Sum、Bucket 布局和正负区间的完整复杂对象, 且在内部标明了其是 `Counter` 还是 `Gauge` 属性.

---

#### 维度二: 客户端/概念模型中的指标类型(语义类型, Metric Types)

* https://prometheus.io/docs/concepts/metric_types/

这是应用开发者在写业务代码暴露指标时定义的 4 种经典语义模型(但请记住, 前 3 种在底层 TSDB 最终全都被当成 `Float64` 存下来了):

1. Counter(计数器)
   * 特点: 单调递增, 只增不减(除非服务重启归零, 即 Reset).
   * 典型场景: 系统接收的 HTTP 请求总数(`http_requests_total`)、系统发生的错误次数.
   * 底层物理值: `Float64`(或者原生直方图中的 Counter Histogram).

2. Gauge(仪表盘/测量值)
   * 特点: 可增可减的瞬时状态值, 忽高忽低.
   * 典型场景: 当前 CPU 使用率、当前内存占用大小(`node_memory_MemFree_bytes`)、当前并发线程数.
   * 底层物理值: `Float64`(或者原生直方图中的 Gauge Histogram).

3. Summary(摘要)
   * 特点: 在客户端本地直接算好百分位数(如 P50, P90, P99)以及总数(count)和总和(sum).
   * 典型场景: 不希望在服务端用 PromQL 计算、而是在应用端就计算好耗时分位数的场景.
   * 底层物理值: 被拆解成一组普通的 `Float64`(例如带 `quantile="0.99"` 标签的浮点序列、`_count` 浮点序列、`_sum` 浮点序列).

4. Histogram(直方图)
   * 特点: 在客户端只分桶统计频数, 由 Prometheus 服务端在查询时通过函数动态计算分位数.
   * 底层物理值:
     * 经典模式下: 拆解成一组独立的 `Float64`(`_bucket`、`_count`、`_sum`).
     * 原生模式下: 存储为单个 `Native Histogram` 复合对象.

### 1. Counter(计数器)

* 业务语义: 只增不减的累加值. 只能增加或者在系统重启时归零(Reset).
* 业务场景: 统计自服务启动以来累计处理的订单总数.
* 暴露文本示例:

```bash
# HELP order_processed_total Total number of orders processed since service startup.
# TYPE order_processed_total counter
order_processed_total{status="success", payment_method="alipay"} 10582
order_processed_total{status="success", payment_method="wechat"} 8421
order_processed_total{status="failed", payment_method="alipay"} 42
```

* 深入解读:
  * `# TYPE order_processed_total counter`: 这行元数据明确告知外部"我是一个 Counter".
  * 数值(如 `10582`)只会不断上升. 如果你想看"当前每秒处理了多少订单", 不是看这个数值有多大, 而是在 PromQL 中使用 `rate(order_processed_total[5m])` 计算其增长速率.
  * 根据规范, Counter 建议以 `_total` 结尾.

---

### 2. Gauge(仪表盘 / 测量值)

* 业务语义: 忽高忽低的瞬时数值. 可以增加、减少或保持不变, 代表系统的当前状态快照.
* 业务场景: 当前连接池活跃连接数、当前处理中的订单队列堆积量、当前内存占用.
* 暴露文本示例:

```bash
# HELP order_processing_queue_size Current number of orders waiting in the queue.
# TYPE order_processing_queue_size gauge
order_processing_queue_size{priority="high"} 3
order_processing_queue_size{priority="normal"} 158

# HELP jvm_memory_used_bytes The amount of used memory.
# TYPE jvm_memory_used_bytes gauge
jvm_memory_used_bytes{area="heap"} 524288000
```

* 深入解读:
  * 数值在下一次抓取时可能变成 `120`, 再下一次可能变成 `200`, 反映的是当下的系统水位.
  * 切忌对 Gauge 类型使用 `rate()` 函数, 因为 Gauge 的变化反映的是状态涨落, 对其求导没有数学意义.

---

### 3. Summary(摘要)

* 业务语义: 统计事件的分布情况. 最大特点是: 分位数(P50、P90、P99)是在客户端(应用程序内存中)直接算好的.
* 业务场景: 统计订单支付耗时. 客户端在滑动时间窗口内(例如过去 10 分钟), 使用流式算法自动计算出 P50、P90、P99 并直接输出.
* 暴露文本示例:

```bash
# HELP order_pay_duration_seconds Order payment duration in seconds.
# TYPE order_pay_duration_seconds summary
order_pay_duration_seconds{quantile="0.5"} 0.082
order_pay_duration_seconds{quantile="0.9"} 0.245
order_pay_duration_seconds{quantile="0.99"} 1.250
order_pay_duration_seconds_sum 845.62
order_pay_duration_seconds_count 5200
```

* 深入解读:
  * 一个 Summary 会暴露三类数据:
    1. 带 `quantile` 标签的浮点值: 客户端算好的分位数(例如 `quantile="0.99"` 为 `1.250` 秒, 表示 99% 的用户支付在 1.25 秒内完成).
    2. `_sum`: 所有请求耗时的总和(`845.62` 秒).
    3. `_count`: 一共发生了多少次支付(`5200` 次).
  * 局限性: Summary 算出的分位数无法在多实例间聚合! 如果有 3 台实例, 你无法将 3 个 P99 直接相加或求平均来得到全局 P99(数学上这是非法的).

---

### 4. Histogram(直方图)

* 业务语义: 同样用于统计事件的分布(如耗时、包大小). 但客户端只负责把观测值投递到不同区间的"桶(Buckets)"中, 不计算分位数; 分位数留给 Prometheus 服务端在查询时动态计算.
* 业务场景: 统计订单创建接口的耗时分布.
* 暴露文本示例:

```bash
# HELP order_create_duration_seconds Order creation latency in seconds.
# TYPE order_create_duration_seconds histogram
order_create_duration_seconds_bucket{le="0.05"} 1200
order_create_duration_seconds_bucket{le="0.1"} 3500
order_create_duration_seconds_bucket{le="0.25"} 4800
order_create_duration_seconds_bucket{le="0.5"} 5100
order_create_duration_seconds_bucket{le="1"} 5180
order_create_duration_seconds_bucket{le="2.5"} 5195
order_create_duration_seconds_bucket{le="+Inf"} 5200
order_create_duration_seconds_sum 425.3
order_create_duration_seconds_count 5200
```

* 深入解读:
  * `le` 代表 "Less than or equal to"(小于等于).
    * `le="0.05"` 为 `1200`: 表示 $\le 0.05$ 秒的请求有 1200 个.
    * `le="0.1"` 为 `3500`: 表示 $\le 0.1$ 秒的请求累计有 3500 个(它包含了前面那 1200 个).
    * `le="+Inf"` 为 `5200`: 小于正无穷大, 数值必定等于总请求数 `_count`.
  * 优势:
    1. 可聚合性: 多台机器的桶可以先用 `sum()` 相加, 再用 Prometheus 的 `histogram_quantile(0.99, ...)` 计算整个集群全局的 P99.
    2. 同时计算吞吐量与平均耗时:
       * 平均耗时 = `rate(order_create_duration_seconds_sum[5m]) / rate(order_create_duration_seconds_count[5m])`.

---

### 4 种类型横向对比与选型指南

| 类型 (Type) | 核心特征 | 客户端开销 | 服务端能否聚合? | 典型场景 |
| :--- | :--- | :--- | :--- | :--- |
| Counter | 单调递增(只增不减) | 极低(原子加法) | 能(直接用 `sum` 或算 `rate` 后聚合) | 请求数、错误数、吞吐量 |
| Gauge | 可升可降的瞬时快照 | 极低(直接赋值) | 能(可求平均值、最大值等) | 内存、CPU、队列深度、连接数 |
| Summary | 客户端直接输出精确分位数 | 较高(需在客户端做复杂流式计算) | 不能(多节点的分位数无法数学合并) | 单机内部性能分析、无需跨机器汇总的场景 |
| Histogram | 客户端分桶计数, 服务端算分位数 | 低(按预设区间累加) | 能(支持跨节点、多维度聚合分位数) | 接口耗时、Payload 大小(生产首选) |

我怎么区分我的查询是 instant query 还是 range query

区分你的查询到底属于 Instant Query(即时查询) 还是 Range Query(区间查询), 有一个极其核心的前提原则需要先建立:

> "是 Instant Query 还是 Range Query, 决定权不在 PromQL 语句本身, 而在查询的发起方式(调用的 API 端点以及携带的参数)."

很多初学者容易误以为写了带有中括号的语句(如 `up[5m]`)就是 Range Query, 这是最常见的误区. 即使你写一模一样的 PromQL(比如 `rate(http_requests_total[5m])`), 它既能被作为即时查询发起, 也能被作为区间查询发起.

我们可以从 HTTP API 调用、Prometheus 自带 Web UI、以及 Grafana / 告警系统 三个维度来清晰区分:

---

### 维度一: 看 HTTP API 端点与参数(最根本的判定依据)

如果你是写代码调 Prometheus, 或者在浏览器 F12 网络面板排查请求:

#### 1. Instant Query(即时查询)

* 调用的 API 端点: `/api/v1/query`
* 传递的必选参数:
  * `query`: 你的 PromQL 表达式
  * `time`(可选): 评估的单点时间戳(如果不传, 默认使用 Prometheus 服务器当前瞬间的时间)
* 示例:

```bash
# 在 2026-10-10 10:00:00 这一秒评估这个指标
curl 'http://localhost:9090/api/v1/query?query=up&time=1791626400'
```

* 核心特征: 它只问一个问题 -- "在某个具体时刻点, 数据是什么?"

#### 2. Range Query(区间查询)

* 调用的 API 端点: `/api/v1/query_range`(注意多了 `_range`)
* 传递的必选参数:
  * `query`: 你的 PromQL 表达式
  * `start`: 查询的开始时间
  * `end`: 查询的结束时间
  * `step`: 时间步长(例如 `15s`、`1m`)
* 示例:

```bash
# 查询过去 1 小时内, 每隔 15 秒评估一次这个指标
curl 'http://localhost:9090/api/v1/query_range?query=rate(http_requests_total[5m])&start=1791622800&end=1791626400&step=15s'
```

* 核心特征: 它问的是 -- "在这一整段时间范围内, 按固定步长采样, 走势是什么?"

---

### 维度二: 看 Prometheus 原生 Web UI 界面

在浏览器打开 Prometheus 页面(默认 `http://localhost:9090`)时, 界面上方有明显的标签页划分:

1. 选中 "Table" 标签页时 $\rightarrow$ 执行的就是 Instant Query
   * 输出的是一个表格, 展示最新一刻各个指标的数值.
   * 下方有一个 `Evaluation time` 输入框, 允许你选择"某一个历史时刻".

2. 选中 "Graph" 标签页时 $\rightarrow$ 执行的就是 Range Query
   * 输出的是折线图.
   * 界面上方会有时间范围选择(如 `1h`, `1d`)以及对应的折线步长, 本质就是在调用 `query_range`.

---

### 维度三: 看上层集成系统(Grafana / 告警规则)

在日常运维开发中, 不同的组件天然对应不同的查询类型:

#### 1. Grafana 中的面板

* 时序趋势图(Time series panel): 一定是 Range Query. Grafana 会把面板的时间范围(例如右上角的 Last 1 hour)和图表分辨率计算为 `start`、`end` 和 `step`, 发往 Prometheus 的 `/api/v1/query_range` 出图.

* 仪表盘/单值卡片(Stat panel, Gauge, Table): 通常是 Instant Query. 在 Grafana 查询编辑器的 Query Options 里, 你可以看到一个 Query Type 开关:
  * 如果选了 `Instant`: Grafana 只调 `/api/v1/query`, 拉取最新时刻的单个数值填入卡片.
  * 如果选了 `Range`: 拉取历史数据绘制 mini sparkline 趋势.

#### 2. Prometheus 告警规则与记录规则(Alerting / Recording Rules)

* 一定是 Instant Query.
* Prometheus 的后台规则评估引擎是周期性运行的(由 `evaluation_interval` 控制, 例如每 15 秒). 引擎在每一个调度周期触发时, 只是针对当前瞬间执行一次单点求值, 判断是否大于阈值.

---

### 常见认知避坑指南

| 场景 | 它是 Instant 还是 Range?  | 为什么?  |
| :--- | :--- | :--- |
| 查询输入框写了 `rate(http_requests_total[5m])`, 在 Table 页点执行 | Instant Query | 虽然内部有 `[5m]` 提取了 5 分钟数据算斜率, 但最终只产出了最新时刻的一个瞬时速率值.  |
| 查询输入框写了 `up`, 在 Graph 页画了一条折线 | Range Query | 虽然 PromQL 极度简单, 但它在过去 1 小时内被按每 15 秒评估了一次, 画出了多点连线.  |
| 在 Graph 页直接写 `http_requests_total[5m]` 报错 | Range Query | 区间查询要求每个时间切片评估出标量或即时向量; 而你的表达式在每个切片又取了一段区间, 维度冲突, 引擎直接报错拒绝.  |

## Expression language data types[](https://prometheus.io/docs/prometheus/latest/querying/basics/#expression-language-data-types)

In Prometheus's expression language, an expression or sub-expression can evaluate to one of four types:

- Instant vector - a set of time series containing a single sample for each time series, all sharing the same timestamp
- Range vector - a set of time series containing a range of data points over time for each time series
- Scalar - a simple numeric floating point value
- String - a simple string value; currently unused

Depending on the use case (e.g. when graphing vs. displaying the output of an expression), only some of these types are legal as the result of a user-specified expression. For [instant queries](https://prometheus.io/docs/prometheus/latest/querying/api/#instant-queries), any of the above data types are allowed as the root of the expression. [Range queries](https://prometheus.io/docs/prometheus/latest/querying/api/#range-queries) only support scalar-typed and instant-vector-typed expressions.

Both vectors and time series may contain a mix of float samples and histogram samples.

## Reconciliation of histogram bucket layouts[](https://prometheus.io/docs/prometheus/latest/querying/basics/#reconciliation-of-histogram-bucket-layouts)

Native histograms can have different bucket layouts, but they are generally convertible to compatible versions to apply binary and aggregation operations to them. Functions acting on range vectors that are applicable to native histograms also perform such reconciliation. In binary operations this reconciliation is performed pairwise, in aggregation operations and functions all histogram samples are reconciled to one compatible bucket layout.

Not all bucket layouts can be reconciled, if incompatible histograms are encountered in an operation, the corresponding output vector element is removed from the result, flagged with a warn-level annotation. More details can be found in the [native histogram specification](https://prometheus.io/docs/specs/native_histograms/#compatibility-between-histograms).

### 一、内容翻译

> 表达式语言数据类型(Expression language data types)
>
> 在 Prometheus 的表达式语言(PromQL)中, 任何一个表达式或子表达式计算求值后的结果必定是以下四种类型之一:
>
> * 即时向量(Instant vector): 一组时间序列, 其中每条时间序列仅包含一个单一的样本值, 且所有时间序列共享完全相同的时间戳.
> * 区间向量(Range vector): 一组时间序列, 其中每条时间序列包含一段时间范围内的一系列数据点(样本序列).
> * 标量(Scalar): 一个单纯的数字浮点值(没有标签和指标名称).
> * 字符串(String): 一个简单的字符串值; 目前尚未实际投入使用.
>
> 根据具体的使用场景(例如: 是在图表中绘制趋势线, 还是在表格中展示单次输出), 只有部分类型可以合法地作为用户最终顶层表达式的返回结果. 对于即时查询(Instant Query), 上述四种数据类型都可以作为根表达式的输出结果. 而区间查询(Range Query)仅支持标量类型(Scalar)和即时向量类型(Instant vector)的表达式.
>
> 向量(Vectors)和时间序列(Time series)中都可以混合包含浮点样本(float samples)和直方图样本(histogram samples).
>
> ---
>
> 直方图桶布局的协调(Reconciliation of histogram bucket layouts)
>
> 原生直方图(Native histograms)可能拥有不同的桶布局(Bucket Layouts, 即桶的边界与分辨率定义), 但它们通常可以被转换为兼容的版本, 从而允许对其执行二元运算(Binary Operations, 如加减乘除)以及聚合操作(Aggregation Operations, 如 `sum()`). 作用于区间向量且适用于原生直方图的函数, 也会执行此类协调操作. 在二元运算中, 这种协调是两两成对(Pairwise)执行的; 而在聚合操作和函数中, 所有的直方图样本都会被统一协调至一个兼容的桶布局.
>
> 并非所有的桶布局都能成功完成协调. 如果在操作过程中遇到了不兼容的直方图, 对应的输出向量元素将直接从最终结果中被剔除(Drop), 并附带一条 `warn`(警告)级别的注解提示. 更多详细细节可参考原生直方图规范.

---

### 二、核心内容总结

1. PromQL 结果系统的四元模型: 表达式无论多复杂, 在 AST(抽象语法树)的任意评估节点上, 求值结果必为 Instant Vector、Range Vector、Scalar、String 之一.
2. 查询模式与数据类型的约束契约:
   * 即时查询(Instant Query) 包容度极高, 4 种类型均可作为最终输出.
   * 区间查询(Range Query) 具有严格限制: 其顶层表达式只允许是 Instant Vector 或 Scalar, 绝对不允许顶层直接返回 Range Vector.
3. 样本类型的多态共存: 向量不仅仅能承载单一数字, 还能混合承载 Native Histogram 复合对象.
4. 原生直方图的对齐(Reconciliation)机制与容错策略:
   * 不同的原生直方图即使精度/分辨率不同, PromQL 引擎也会尝试在数学运算前自动将它们的桶"对齐/降级合并".
   * 静默容错降级: 若发生无法协调的不兼容情况, Prometheus 不会让整个查询崩溃报错(Fail), 而是选择丢弃该元素并给出 Warning 注解.

---

### 三、这段内容想表达的深层含义(底层硬核原理)

#### 1. 为什么"区间查询(Range Query)"不能以 Range Vector 作为顶层结果?

很多初学者最常犯的错误, 就是在 Grafana 或 Prometheus 图表(Graph)里直接输入带中括号的表达式, 例如: `http_requests_total[5m]`, 然后报错: `expression type "range vector" is invalid for range query`.

* 背后的原理: 区间查询本质上是"沿着时间轴以步长(step)多次执行评估".
* 如果每个步长返回的是一个 Instant Vector(单一时刻的一个点), 那么随着时间推移, Prometheus 就能把这些点连成一条二维走势线.
* 但如果你在区间查询里输入 `[5m]`(Range Vector), 这意味着在每一个时间步长点上, 你都返回了一个点阵集合(二维数据); 再叠加上时间推进步长, 就变成了三维立方体数据. Prometheus 的时序绘图引擎只支持二维曲线展示, 因此语法层直接禁止顶层 Range Vector 作为区间查询结果. 区间向量只能作为某些函数(如 `rate()`、`increase()`)的内部输入参数, 最终被降维压缩为即时向量!

#### 2. 原生直方图的"桶布局协调(Reconciliation)"是在解决什么数学难题?

在经典直方图中, 两个指标相加(`sum(metric_a + metric_b)`), 只是普通浮点数的加法, 因为所有的桶边界标签(如 `le="0.1"`)是死板、完全对齐的.

但在原生直方图(Native Histogram)中, 桶是动态指数增长的(通过 `Schema` 定义, 例如 Schema 1 代表桶边界按 $\sqrt{2}$ 递增, Schema 2 按 $\sqrt[4]{2}$ 递增).
* 如果服务 A 的直方图精度很高(细粒度桶, Schema 3), 而服务 B 的直方图精度稍低(粗粒度桶, Schema 1), 你执行 `metric_a + metric_b` 或 `sum(metric)` 时, 两个直方图的桶边界根本切不齐.
* Reconciliation 的含义: Prometheus 引擎会自动充当"数学裁缝", 自动将高精度的桶"降采样/合并"到低精度桶的边界上, 让两者的直方图布局达成一致后, 再执行向量加法或聚合.

#### 3. 为什么不兼容时选择"剔除元素 + 警告", 而不是抛出致命错误(Error)?
在分布式高并发监控系统中, 如果几千台机器里只有一台机器上报了损坏或极度异常、无法对齐的直方图, 若直接报 500 导致整个 PromQL 查询失败, 你的监控大盘会全屏变红挂掉.
因此, Prometheus 采取了优雅降级(Graceful Degradation)策略: 扔掉那一个不兼容的序列, 保证其他 99.9% 正确序列能继续出图, 同时打上 warning 告诉你这里有数据被丢弃了.

### 四、从上述内容中我们可以知道什么?(生产实践指导)

| 知识点 | 文档暴露的规则 | 给日常开发/运维排查的黄金准则 |
| :--- | :--- | :--- |
| 查询报错避坑 | 区间查询只支持 Scalar 和 Instant Vector.  | 切记: 在 Grafana 配图表(本质是 Range Query)时, 表达式最外层绝不能带中括号 `[5m]`. 如果带了中括号, 外层必须包裹函数(如 `rate(...)`、`sum_over_time(...)`), 将其降维为 Instant Vector.  |
| 标量的独立绘制 | Range Query 接受 Scalar.  | 在 Grafana 中, 你可以直接在查询框里输入纯数字标量(如输入 `100` 或 `0.95`), 它会在图表上绘制出一条固定水平阈值基准线(Baseline).  |
| 即时查询的灵活性 | Instant Query 允许任何类型(包括 Range Vector 和 String).  | 如果你想一次性把过去 5 分钟的所有原始数据点全部拉取出来 dump 到外部系统, 直接调 HTTP API 的即时查询接口(`/api/v1/query?query=up[5m]`)即可, 它完全支持.  |
| 原生直方图聚合成本 | 原生直方图的二元运算与聚合需要先做布局协调(Reconciliation).  | 虽然原生直方图节省了网络和存储基数, 但在执行跨大量不同分辨率指标的聚合计算(`sum()`)时, 会在查询节点引发额外的 CPU 动态合并开销; 业务 SDK 最好统一配置相同的 Histogram Schema.  |
| 静默丢弃与监控告警 | 无法对齐的原生直方图会被默默丢弃并转为 warning.  | 对原生直方图配置关键 SLA/SLO 告警时, 要注意 API 返回结构中的 `warnings` 字段; 如果业务改动导致局部桶布局严重不兼容, 部分实例的指标可能会无声无息地从告警计算中消失.  |

---------------------------------------------------------------------------------------------------------

> 在 Prometheus 的表达式语言(PromQL)中, 任何一个表达式或子表达式计算求值后的结果必定是以下四种类型之一:
>
> * 即时向量(Instant vector): 一组时间序列, 其中每条时间序列仅包含一个单一的样本值, 且所有时间序列共享完全相同的时间戳.
> * 区间向量(Range vector): 一组时间序列, 其中每条时间序列包含一段时间范围内的一系列数据点(样本序列).
> * 标量(Scalar): 一个单纯的数字浮点值(没有标签和指标名称).
> * 字符串(String): 一个简单的字符串值; 目前尚未实际投入使用.

为了让你直观理解这四种数据类型的本质差异, 我们以 Prometheus 官方 HTTP 查询 API(`/api/v1/query`)在底层真实返回的 JSON 数据结构为参照, 通过具体的数据示例逐一模拟展示.

假设当前系统中有两台主机: `node1 (192.168.1.10)` 和 `node2 (192.168.1.11)`.

---

### 1. 即时向量(Instant Vector)

* 定义要点: 多条时序序列, 每条序列只有一个值, 且所有值对应的时间戳完全一样(切片视角).
* 触发表达式: `http_requests_total{status="200"}`
* 评估时间戳: `1700000000`(某一个指定的瞬间)
* 模拟返回数据:

```json
{
  "resultType": "vector",
  "result": [
    {
      "metric": {
        "__name__": "http_requests_total",
        "instance": "192.168.1.10:8080",
        "status": "200"
      },
      "value": [ 1700000000, "1542" ]  // [时间戳, 单一指标值]
    },
    {
      "metric": {
        "__name__": "http_requests_total",
        "instance": "192.168.1.11:8080",
        "status": "200"
      },
      "value": [ 1700000000, "2018" ]  // 时间戳相同, 单一指标值
    }
  ]
}
```

* 形象理解: 就像给所有机器拍了一张集体快照. 在按下快门的那一瞬间(`1700000000`), 机器 A 报了一个数字, 机器 B 报了一个数字.

---

### 2. 区间向量(Range Vector)

* 定义要点: 多条时序序列, 每条序列包含过去一段时间范围内的一组/一段历史数据点集合. 在 PromQL 中通常带有时间选择范围括号(例如 `[1m]`).
* 触发表达式: `http_requests_total{status="200"}[1m]`
* 评估时间戳: 以 `1700000000` 为基准, 拉取过去 1 分钟(假设抓取间隔是 15 秒)
* 模拟返回数据:

```json
{
  "resultType": "matrix",
  "result": [
    {
      "metric": {
        "__name__": "http_requests_total",
        "instance": "192.168.1.10:8080",
        "status": "200"
      },
      // 注意: 这里不是单一的 "value", 而是包含了多个点的数组 "values"
      "values": [
        [ 1700000000 - 45, "1510" ],
        [ 1700000000 - 30, "1521" ],
        [ 1700000000 - 15, "1530" ],
        [ 1700000000,      "1542" ]
      ]
    },
    {
      "metric": {
        "__name__": "http_requests_total",
        "instance": "192.168.1.11:8080",
        "status": "200"
      },
      "values": [
        [ 1700000000 - 45, "1980" ],
        [ 1700000000 - 30, "1995" ],
        [ 1700000000 - 15, "2005" ],
        [ 1700000000,      "2018" ]
      ]
    }
  ]
}
```

* 形象理解: 这不再是一张照片, 而是每台机器各自拍了一段 1 分钟的小视频.
* 核心注意点: 区间向量包含多个点, 因此它不能直接画图(前端出图不知道该选哪个点作为此时的 Y 轴), 它必须被 `rate()`、`increase()` 或 `avg_over_time()` 这类函数消费并压缩/折叠(Fold)成一个即时向量.

---

### 3. 标量(Scalar)

* 定义要点: 一个纯粹的双精度浮点数, 没有任何标签(Labels), 也没有指标名(Metric Name). 它完全脱离了具体的机器、实例或服务上下文.
* 触发表达式:
  * 纯数值: `100` 或 `0.75`
  * 或者使用 `scalar()` 函数提取单个值: `scalar(sum(up))`
* 评估时间戳: `1700000000`
* 模拟返回数据:

```json
{
  "resultType": "scalar",
  // 没有任何 metric 标签对象, 直接就是一个 [时间戳, 纯数字] 数组
  "result": [ 1700000000, "42.5" ]
}
```

* 形象理解: 它就是一个飘在空中的常数或纯数字.
* 典型用途:
  1. 作为数学运算的乘数或分母, 例如把字节转为兆字节: `node_memory_MemFree_bytes / (1024 * 1024)`, 这里的 `1024 * 1024` 计算出的就是标量.
  2. 在绘图工具中画固定阈值参考红线(例如查询表达式直接写: `85`, 画出 85% 水位线).

---

### 4. 字符串(String)

* 定义要点: 一个纯文本字符串值. 正如官方文档所言: *"currently unused"*. 目前它在 Prometheus 生产环境的监控、告警、画图中几乎没有实际业务用途, 主要是 Prometheus 词法解析器(Lexer/Parser)在语法层面做了预留, 用于解析双引号/单引号包裹的文本字面量.
* 触发表达式: `"Hello World"` 或 `'api_timeout_alert'`
* 评估时间戳: `1700000000`
* 模拟返回数据:

```json
{
  "resultType": "string",
  // 同样没有 metric 对象, 直接是 [时间戳, 字符串内容]
  "result": [ 1700000000, "Hello World" ]
}
```

* 形象理解: PromQL 语法树里的"占位符类型". 你无法对它进行时序运算, 也无法画图, 它只是词法分析阶段的字面量产物.

---

### 四种类型直观横向比对

| 类型 | 是否包含 Labels(指标标签)? | 包含的数据点数量 | 内部结构表现 (JSON 视角) | 常用场景 |
| :--- | :--- | :--- | :--- | :--- |
| Instant Vector | 有(描述不同的序列) | 每个序列 1 个点 | `[ {"metric": {...}, "value": [t, v]} ]` | 监控报警、当前状态图表展示 |
| Range Vector | 有(描述不同的序列) | 每个序列 N 个点(一段时间范围) | `[ {"metric": {...}, "values": [[t1, v1], [t2, v2]...]} ]` | 供 `rate()`、`sum_over_time()` 等计算速率/区间聚合 |
| Scalar | 无(纯数值) | 全局仅 1 个点 | `[ t, v ]` | 阈值基准线、算术四则运算(如乘除转换单位) |
| String | 无 | 1 个纯字符串 | `[ t, "str" ]` | PromQL 语法预留, 生产环境几乎不直接使用 |

### 问题 2: 我怎么查询我的某一个指标在 TSDB 存储中使用的物理类型是什么?

在实际排查中, 区分某个指标存储的是普通的 `Float64` 还是 `Native Histogram`, 最直观且准确的办法有以下几种:

#### 方法一: 通过 HTTP API 查询返回结构(最底层的权威判定)

通过 `curl` 或浏览器开发者工具向 `/api/v1/query` 发起即时查询:

```bash
curl -g 'http://localhost:9090/api/v1/query?query=my_metric_name'
```

观察返回 JSON 中每个时间序列的键:

* `Float64`: 返回的键是 `value`, 内部是一个双元素数组 `[timestamp, "数值字符串"]`.

```json
{
    "metric": {
        "__name__": "my_metric_name",
        ...
    },
    "value": [
        1700000000,
        "123.45"
    ]
}
```

* `Native Histogram`: 返回的键是 `histogram`, 内部是一个包含 `count`、`sum`、`buckets` 等字段的对象结构.

```json
{
    "metric": {
        "__name__": "my_metric_name",
        ...
    },
    "histogram": [
        1700000000,
        {
            "count": "10",
            "sum": "1.392",
            "buckets": [
                ...
            ]
        }
    ]
}
```

#### 方法二: 在 Prometheus Web UI(Table 标签页)观察显示形式

在 Prometheus 自带的 Web UI 中切换到 Table 标签页, 直接输入指标名称查询:

* 如果右侧 Value 列显示的是一个普通的阿拉伯数字(如 `42`、`0.05`), 则为 `Float64`.
* 如果显示的是带有直方图特有结构的文本(如带有 count、sum 以及类似 `{count: ..., sum: ..., buckets: [...]}` 的展开样式), 则为 `Native Histogram`.

#### 方法三: 使用原生直方图专有内置函数进行探查

PromQL 提供了一些仅针对原生直方图生效的函数(如提取直方图观测总数的 `histogram_count()`、提取总和的 `histogram_sum()`, 或提取分位数的 `histogram_fraction()`):

* 如果执行 `histogram_count(my_metric_name)`:
  * 能正常返回数值: 说明指标存储的是 Native Histogram.
  * 返回空结果或警告: 说明该指标是普通的 Float64(对于经典直方图, 你必须去查带 `_count` 后缀的具体浮点序列, 而不能对其桶指标使用原生函数).

### 问题 3: 对于某个查询表达式, 我如何辨别有哪些子查询(子表达式), 以及它们返回什么类型?

在 PromQL 中, 要区分两个概念:

* 子表达式(Sub-expression): 嵌套在主表达式内部的运算单元或函数调用(例如 `rate(...)` 内部的 `metric[5m]`).
* 子查询(Subquery, 特指语法): PromQL 中带有两次区间范围与步长定义的特殊语法, 形如 `<expression>[<range>:<resolution>]`.

判断表达式的层级结构及其返回类型, 主要依靠 "自内向外(Bottom-up)的 AST 语法树拆解法".

#### 核心推导规则清单(判断类型时查阅)

1. 选择器规则:
   * 指标不带方括号(如 `up`、`http_requests_total`) $\rightarrow$ Instant vector.
   * 指标带方括号(如 `http_requests_total[5m]`) $\rightarrow$ Range vector.
2. 函数规则:
   * 必须吃 Range vector、吐出 Instant vector 的函数: `rate()`、`irate()`、`increase()`、`changes()`、`*_over_time()`(如 `sum_over_time`).
   * 必须吃 Instant vector、吐出 Instant vector 的函数: `histogram_quantile()`、`label_replace()`、`abs()` 等数学修饰函数.
3. 聚合操作规则:
   * `sum()`、`avg()`、`max()`、`min()`、`topk()` 等聚合算子: 输入 Instant vector $\rightarrow$ 输出 Instant vector.
4. 子查询语法规则:
   * 形如 `(expression)[range:resolution]`: 将一个 Instant vector 表达式在历史时间轴上按 resolution 步长评估, 最终生成一个 Range vector.
5. 纯数字规则:
   * 单独出现的无标签数字(如 `100`、`0.95`) $\rightarrow$ Scalar.

---

#### 实例拆解演示

##### 示例 A(常见速率聚合):

```promql
sum(rate(http_requests_total{status="500"}[5m])) > 10
```

我们从最深层向最外层逐层拆解:

1. 第一层(叶子节点):
   * 子表达式: `http_requests_total{status="500"}[5m]`
   * 类型推导: 末尾带有区间选择符 `[5m]`.
   * 返回类型: Range vector.

2. 第二层:
   * 子表达式: `rate(...)`
   * 类型推导: `rate()` 函数接收刚才的 Range vector, 计算每秒增长率并折叠时间窗口.
   * 返回类型: Instant vector.

3. 第三层:
   * 子表达式: `sum(...)`
   * 类型推导: `sum` 聚合算子接收上面的 Instant vector, 将多条时序合并.
   * 返回类型: Instant vector.

4. 第四层(最外层/最终查询):
   * 表达式: `... > 10`
   * 类型推导: Instant vector 与 Scalar(纯数字 `10`)进行二元比较过滤.
   * 最终返回类型: Instant vector(保留了符合条件的序列快照).

---

##### 示例 B(包含真正 PromQL Subquery 语法的复杂表达式):

```promql
max_over_time(rate(http_requests_total[1m])[1h:5m])
```

1. 第一层:
   * 子表达式: `http_requests_total[1m]`
   * 返回类型: Range vector.

2. 第二层:
   * 子表达式: `rate(...)`
   * 返回类型: Instant vector.

3. 第三层(子查询语法生效点):
   * 子表达式: `rate(...)[1h:5m]`
   * 类型推导: 这是一个 PromQL Subquery. 它将第二层产出的 Instant vector 表达式, 在过去 1 小时内按每 5 分钟的步长评估一次, 把多次计算的结果串联起来.
   * 返回类型: Range vector(矩阵点阵).

4. 第四层(最外层/最终查询):
   * 表达式: `max_over_time(...)`
   * 类型推导: `*_over_time` 函数接收 Range vector, 取出每个序列在窗口内的最大值, 压平成单点.
   * 最终返回类型: Instant vector.

---

#### 总结辨别技巧

* 看中括号: 凡是表达式最外层带了单个中括号且没有被聚合/计算函数包裹(如 `[5m]` 或 `[1h:5m]`), 它产出的必然是 Range vector.
* 看能否画图: 如果把这个子表达式单独复制到 Prometheus Web UI 的 Graph 标签页执行:
  * 能直接画出折线图 $\rightarrow$ 必然是 Instant vector 或 Scalar.
  * 报错提示 `expression type "range vector" is invalid for range query` $\rightarrow$ 必然是 Range vector.

对于使用 prometheus, 客户端使用客户端/概念模型中的指标类型(语义类型, Metric Types)输出指标, prometheus 抓取这些指标, 不同语义类型的指标在 TSDB 存储中使用不同的物理类型进行存储, 两种物理类型分别是`Float64`(标量浮点型)和`Native Histogram`(原生直方图类型).

prometheus 是如何判断到底使用哪种物理类型来存储这些指标的?

在底层实现中, Prometheus 既不会靠猜测, 也不是靠指标名称来决定物理存储类型.

决定一个指标到底存为 `Float64` 还是 `Native Histogram`, 完全取决于抓取协议的内容协商(Content Negotiation) 以及解析器从网络报文中读到的数据结构.

整个判定流程可以拆解为以下三个核心阶段:

---

### 一、默认铁律: 除直方图外, 一律扁平化为 `Float64`

Prometheus 的核心架构设计中有一条基本原则:

> 除了原生直方图, TSDB 会将所有的语义类型(Counter、Gauge、Summary 以及经典直方图)全部抹去类型差异, 无条件存为 `Float64`.

* Counter / Gauge: 客户端报上来的本来就是单值浮点数, TSDB 直接存为 `Float64`.
* Summary: 虽然是复合统计, 但客户端在传输时已经把它拆成了 `_count`、`_sum` 和多个带 `quantile` 标签的独立单值行, Prometheus 解析后全当成普通的 `Float64` 存储.
* 经典直方图(Classic Histogram): 同样被拆成了 `_bucket`、`_count`、`_sum` 等独立的单行, Prometheus 一律作为普通的 `Float64` 存储.

---

### 二、触发 `Native Histogram` 物理存储的判定链路

只有当 Prometheus 同时满足以下 3 个关卡时, 才会动用 `Native Histogram` 复合类型来存储指标:

```bash
[关卡 1: 服务端开启特性] ──► [关卡 2: HTTP 协议协商 Protobuf] ──► [关卡 3: 解析器识别到原生直方图字段]
       │                                │                                    │
       否                               否                                   否
       ▼                                ▼                                    ▼
  存为 Float64                     存为 Float64                         存为 Float64
```

#### 关卡 1: Prometheus 启用了原生直方图支持

* 原生直方图属于高级特性, Prometheus 需要通过参数开启(如启动参数 `--enable-feature=native-histograms`, 或在抓取配置中声明支持).
* 若未开启: Prometheus 甚至不会向客户端请求原生直方图数据, 所有数据走传统流程(全存为 `Float64`).

#### 关卡 2: 抓取时的 HTTP 协议协商(Content Negotiation)

文本格式(Prometheus Text 0.0.4 等)为了保证人类可读, 并不支持高效传输原生直方图的复杂数据结构. 原生直方图必须依赖二进制的 Protobuf 格式传输.

1. 当开启该特性后, Prometheus 在访问客户端的 `/metrics` 接口时, 会在 HTTP 请求头中声明:

```http
Accept: application/vnd.google.protobuf; proto=io.prometheus.client.MetricFamily; encoding=delimited, ...
```
   明确告诉客户端: "我优先需要 Protobuf 格式".

2. 客户端判定:
   * 如果客户端 SDK 支持并配置了原生直方图, 就会响应 Protobuf 格式数据.
   * 如果客户端老旧, 只支持返回传统的 Text 格式, 协商降级为文本, 进入经典模式(全存为 `Float64`).

#### 关卡 3: 数据包内部字段的类型识别(Parser 解析分流)

当 Prometheus 收到 Protobuf 数据包(即 `MetricFamily` 消息体)后, 解析器(Scrape Parser)开始反序列化:

* 分支 A(普通指标): 读取到 `Counter`、`Gauge`、`Untyped` 字段 $\rightarrow$ 调用 TSDB 的 `Appender.Append()`, 以 `Float64` 存入.

* 分支 B(经典直方图): 读取到 `Histogram` 消息, 但内部只有固定的 `Bucket` 列表(包含 `upper_bound`) $\rightarrow$ 拆解为多个时间序列, 调用普通的 `Append()`, 以 `Float64` 存入.

* 分支 C(原生直方图): 读取到 `Histogram` 消息, 且包含了原生直方图专属字段(例如: `schema` 指数因子、`positive_span`、`negative_span` 等稀疏桶布局字段) $\rightarrow$ 解析器识别出这是一个 Native Histogram, 此时会调用 TSDB 专用的 `Appender.AppendHistogram()` 接口, 将完整的直方图对象直接写入 TSDB 的 `Native Histogram` 专有数据块中!

---

### 三、常见边界与配置干预: 如果客户端同时暴露了两种直方图呢?

现代的 Prometheus 客户端 SDK(如 Go/Java SDK)为了兼容新老系统, 常常采用 双重暴露(Dual Exposition): 同一个直方图, 既暴露出经典直方图的 `_bucket` 浮点数, 又包含原生直方图的 Protobuf 数据.

Prometheus 内部通过抓取配置项来决定行为:
1. `scrape_classic_histograms: false`(推荐默认做法):
   Prometheus 识别到原生直方图后, 会自动丢弃那些带有 `_bucket`、`_sum`、`_count` 的冗余浮点序列, 只保留一条原生直方图时间序列存储进 TSDB.
2. `scrape_classic_histograms: true`:
   Prometheus 会进行"双写": 既把原生直方图存为一条 `Native Histogram` 物理序列, 又把经典拆解后的桶序列存为多条 `Float64` 物理序列.

---

### 总结对照卡

| 客户端指标语义类型 | 采用的数据协议 | 是否携带 Native 字段?  | TSDB 最终存储的物理类型 |
| :--- | :--- | :--- | :--- |
| Counter | 任意(Text 或 Protobuf) | 否 | `Float64` |
| Gauge | 任意(Text 或 Protobuf) | 否 | `Float64` |
| Summary | 任意(Text 或 Protobuf) | 否 | `Float64`(被拆为多个 Float 序列) |
| Classic Histogram | Text 或旧 Protobuf | 否 | `Float64`(被拆为多个 Float 序列) |
| Native Histogram | Protobuf | 是(包含 schema / 动态桶边界) | `Native Histogram`(单序列复合对象) |

请问下面的四种表达式是否合法, 如果合法, 表达的含义是什么
`http_requests_total[1m]`
`http_requests_total[1m:5m]`
`rate(...)[1h]`
`rate(...)[1h:5m]`

这四个表达式涉及到 PromQL 中最关键的语法分水岭: 区间选择器(Range Selector) 与 子查询(Subquery) 的本质区别.

作为 Prometheus 开发人员, 我为你逐一剖析它们的合法性、底层执行逻辑及具体含义:

---

### 1. `http_requests_total[1m]`

* 合法性: 语法完全合法(但受执行模式约束).
* 语法类型: 区间向量选择器(Range Vector Selector).
* 表达的含义:
  * 它直接作用于物理指标名 `http_requests_total`.
  * 含义是: 从当前评估时间戳向前回溯 1 分钟(1m), 提取该时间窗口内的所有原始抓取样本点(Raw Samples).
  * 返回数据类型: 区间向量(Range vector).
* 使用注意点:
  * 合法场景: 在即时查询(Instant Query / Table 标签页)中独立运行; 或者作为 `rate()`、`increase()`、`avg_over_time()` 等函数的入参.
  * 报错场景: 如果你把它作为顶层表达式在区间查询(Range Query / Graph 绘图页)中直接执行, Prometheus 会报错拒绝(因为绘图引擎无法将包含多点阵列的区间向量直接投影为单条二维曲线).

---

### 2. `http_requests_total[1m:5m]`

* 合法性: 语法合法, 但语义极不合理(逻辑反模式 Anti-pattern).
* 语法类型: 子查询(Subquery).
  * 子查询的标准语法结构为: `<instant_query>[<range>:<resolution>]`.
  * 因为 `http_requests_total` 自身是一个合法的即时向量(Instant vector), 语法树能解析通过.
* 表达的含义:
  * 含义是: 在过去 1 分钟(Range=1m) 的时间跨度内, 以 5 分钟(Resolution=5m) 为步长, 对 `http_requests_total` 执行单点评估.
  * 返回数据类型: 区间向量(Range vector).
* 为什么说它极不合理?
  1. 大材小用: 子查询通常用于对"函数或复杂表达式的结果"进行时间切片(模拟 Recording Rule). 对于裸指标, 直接用第 1 个表达式 `[1m]` 获取真实抓取点即可, 无需开销巨大的子查询引擎.
  2. 分辨率大于时间窗口(Resolution > Range): 评估步长(5m)比总时间窗口(1m)还要大. 这意味着在 1 分钟的狭窄窗口内, 按 5 分钟对齐步长采样, 很可能只能捕获到 0 个或至多 1 个评估点, 完全失去了采样的意义.

---

### 3. `rate(...)[1h]`

* 合法性: 完全不合法! (PromQL 语法解析错误 Parse Error)
* 为什么报错?
  * `[1h]` 是纯区间选择器, 在 PromQL 语法规范中, 它只能且仅能直接挂在指标选择器(Metric Selector)后面(如 `node_cpu[1h]`).
  * `rate(...)` 是一个函数调用, 它吐出的计算结果是一个即时向量(Instant Vector).
  * PromQL 严禁在函数、二元算子或聚合表达式后面直接挂单时间区间的方括号 `[1h]`.
* 控制台错误提示:
  Prometheus 会直接中断解析并报错:
  `parse error: ranges only allowed on vector selectors`(区间只允许直接作用于向量选择器).
* 如何修复?
  如果你想对 `rate(...)` 的结果回溯 1 小时的历史, 必须使用包含冒号 `:` 的子查询语法(见第 4 个表达式).

---

### 4. `rate(...)[1h:5m]`

* 合法性: 完全合法! 且是标准的经典用法(前提是 `rate(...)` 内部入参正确, 例如 `rate(http_requests_total[5m])`).
* 语法类型: 子查询(Subquery).
* 表达的含义:
  * 内部的 `rate(...)` 计算出服务请求的瞬时速率(Instant vector).
  * 外层的 `[1h:5m]` 驱动 Prometheus 启动子查询引擎: 在过去 1 小时(Range=1h) 的时间范围内, 每隔 5 分钟(Resolution=5m) 运行一次内部的 `rate(...)` 计算, 从而生成约 12~13 个计算结果点.
  * 返回数据类型: 区间向量(Range vector).
* 典型应用场景:
  由于它返回的是区间向量, 它通常不会单独作为终点, 而是作为外层时间聚合函数(`*_over_time`)的输入:
  ```promql
  # 统计过去 1 小时内(按 5 分钟步长评估), 该接口出现的最高请求速率是多少
  max_over_time(rate(http_requests_total[5m])[1h:5m])
  ```

---

### 核心记忆速查表

| 表达式 | 语法是否合法 | 核心性质 | 返回类型 | 底层规则总结 |
| :--- | :---: | :--- | :--- | :--- |
| `http_requests_total[1m]` | 合法 | 原生区间选择器 | Range vector | 只能直接挂在裸指标后面, 提取原始存储样本.  |
| `http_requests_total[1m:5m]` | 合法(但无意义) | 裸指标子查询 | Range vector | 语法允许, 但裸指标无需子查询, 且步长大于窗口属于反模式.  |
| `rate(...)[1h]` | ❌ 非法 | 语法错误 | 无(报错) | 严禁对函数/复合表达式直接使用无冒号的 `[1h]`.  |
| `rate(...)[1h:5m]` | 合法 | 标准函数子查询 | Range vector | 对函数表达式做时间切片必须带冒号声明子查询 `[Range:Resolution]`.  |

> 在 Prometheus 的表达式语言(PromQL)中, 任何一个表达式或子表达式计算求值后的结果必定是以下四种类型之一:
>
> * 即时向量(Instant vector): 一组时间序列, 其中每条时间序列仅包含一个单一的样本值, 且所有时间序列共享完全相同的时间戳.
> * 区间向量(Range vector): 一组时间序列, 其中每条时间序列包含一段时间范围内的一系列数据点(样本序列).
> * 标量(Scalar): 一个单纯的数字浮点值(没有标签和指标名称).
> * 字符串(String): 一个简单的字符串值; 目前尚未实际投入使用.

Prometheus 中有操作符, 例如加, 减, 大于等, 还有一些函数, 操作符和函数能处理的表达式或子表达式是不是和他们的返回值类型有关?

是的, 完全正确!

在 PromQL 中, 每一个操作符(Operators)和函数(Functions)都有极其严格的"类型契约(Type Contract)".

PromQL 在执行时会对抽象语法树(AST)进行类型检查: 某个操作符或函数能否处理你的子表达式, 完全取决于该子表达式求值后返回的数据类型是什么.  如果输入的类型不匹配, PromQL 会直接在解析或执行期抛出类型不匹配错误(Type Error).

为了让你在写 PromQL 时胸有成竹, 我们把这些操作符和函数的"类型规则"进行系统性拆解:

---

### 一、 操作符的类型契约(Binary / Unary Operators)

PromQL 中的操作符主要有三类: 算术操作符、比较操作符、逻辑/集合操作符. 它们对输入类型的要求截然不同:

#### 1. 算术二元操作符(`+`, `-`, `*`, `/`, `%`, `^`)
它们只允许处理以下 3 种类型组合, 绝对不能处理区间向量(Range vector):
* `Scalar` 与 `Scalar`: 计算两个纯数字, 返回 `Scalar`(例如: `1 + 2` $\rightarrow$ `3`).
* `Instant vector` 与 `Scalar`: 将标量与向量中的每个序列的样本值依次运算, 保留原标签, 返回 `Instant vector`(例如: `node_memory_free / 1024`).
* `Instant vector` 与 `Instant vector`: 依据标签匹配规则(如 `on()` / `ignoring()`)在两个即时向量间做两两计算, 返回 `Instant vector`.

> ❌ 典型错误: `http_requests_total[5m] + 1`
> 原因: `[5m]` 产出的是 Range vector, 算术操作符不能作用于 Range vector, 解析器直接报错: `binary expression must not contain range vector`.

#### 2. 比较二元操作符(`==`, `!=`, `>`, `<`, `>=`, `<=`)
其类型规则与算术操作符类似, 也只接受 `Scalar` 和 `Instant vector`:
* 可以用来做过滤(例如 `up == 0`, 过滤出值为 0 的序列, 返回 `Instant vector`);
* 加上 `bool` 修饰符后做布尔判定(例如 `up == bool 0`, 返回值为 0 或 1 的 `Instant vector`).
* ❌ 同样严禁传入 Range vector.

#### 3. 集合/逻辑操作符(`and`, `or`, `unless`)
它们的类型约束最为苛刻:
* 只允许: `Instant vector` 与 `Instant vector` 之间进行集合交并补操作.
* ❌ 不能处理 Scalar: 例如写 `1 and 2` 会直接报语法错误!
* ❌ 不能处理 Range vector.

---

### 二、 内置函数的类型契约(Functions)

PromQL 内置函数是类型敏感度最高的区域, 大体可以分为以下几大阵营:

#### 1. "专门消费 Range vector" 的函数
这批函数的作用通常是"降维" -- 把一段时间范围内的多个点, 压缩或折算为一个单点值.
* 典型函数:
  * 速率与增量计算: `rate()`, `irate()`, `increase()`, `resets()`, `changes()`
  * 历史时间聚合(Rollup 系列): `avg_over_time()`, `max_over_time()`, `sum_over_time()`, `quantile_over_time()`
* 类型契约:
  * 入参: 必须是 `Range vector`.
  * 返回值: 转换为 `Instant vector`.
* ❌ 典型错误: `rate(up)`
  > 报错: `expected type range vector in call to function "rate", got instant vector`. 因为 `up` 是 Instant vector, `rate` 无法计算速率.

#### 2. "专门消费 Instant vector" 的函数
这批函数处理单时刻的切片快照, 用于数学转换、标签处理或分位数估算.
* 典型函数:
  * 数学修饰: `abs()`, `ceil()`, `floor()`, `round()`, `clamp()`
  * 标签修改: `label_replace()`, `label_join()`
  * 直方图分位数: `histogram_quantile()`(第一个参数是 Scalar, 第二个参数必须是 Instant vector)
* 类型契约:
  * 入参: `Instant vector`.
  * 返回值: `Instant vector`.
* ❌ 典型错误: `abs(http_requests_total[5m])`
  > 报错: `abs` 期待 Instant vector, 你给了一个 Range vector.

#### 3. "类型转换 / 桥接" 函数
PromQL 提供了少数几个专门用于打破类型边界的函数:
* `scalar(Instant vector)`:
  * 入参: 只有一个序列的 `Instant vector`.
  * 返回值: 将这个序列的样本值剥离标签, 提取成纯数字 `Scalar`.
  * (如果传入的向量有 2 个及以上序列, 会返回 `NaN`).
* `vector(Scalar)`:
  * 入参: 纯数字 `Scalar`.
  * 返回值: 将其包装为一个无任何标签的 `Instant vector`.

---

### 三、 聚合操作符的类型契约(Aggregation Operators)

像 `sum()`, `avg()`, `min()`, `max()`, `count()`, `topk()` 这些聚合算子:
* 类型契约:
  * 入参: 只能是 `Instant vector`.
  * 返回值: 聚合后的 `Instant vector`.
* ❌ 常见概念混淆:
  * 想算过去 5 分钟的 CPU 平均值, 写成了 `avg(node_cpu_seconds_total[5m])` $\rightarrow$ 报错!
  * 正解: 横向(跨序列)聚合用 `avg(...)`, 时间纵向聚合必须用时间函数 `avg_over_time(...)`.

---

### 总结: 高级开发者的 PromQL"搭积木"心智模型

你可以把 PromQL 的每个子表达式想象成带有凹凸接口的乐高积木:

```bash
[ 指标选择器: up ]                 ──► 产出 Instant vector
        │
        ├── 套上 [5m]              ──► 变为 Range vector
        │       │
        │       ├── 输入 rate()    ──► 压缩降维为 Instant vector
        │       │       │
        │       │       ├── 乘以 100 (操作符 *) ──► 仍是 Instant vector
        │       │       │
        │       │       └── 输入 sum()           ──► 聚合为 Instant vector
        │       │                                       │
        │       │                                       └── 满足区间查询/画图要求!
        │       │
        │       └── 直接输入 + 1    ──► ❌ 接口不匹配(Boom! 报错)
        │
        └── 直接输入 rate()        ──► ❌ 接口不匹配(Boom! 报错)
```

结论: 编写 PromQL 时, 你脑海中只要时刻追踪每一个子表达式"当前被求值成了 4 种类型中的哪一种", 就永远不会写出报语法或类型错误的 PromQL 查询.

## Literals[](https://prometheus.io/docs/prometheus/latest/querying/basics/#literals)

The following section describes literal values of various kinds. Note that there is no "histogram literal".

### String literals[](https://prometheus.io/docs/prometheus/latest/querying/basics/#string-literals)

String literals are designated by single quotes, double quotes or backticks.

PromQL follows the same [escaping rules as Go](https://golang.org/ref/spec#String_literals) . For string literals in single or double quotes, a backslash begins an escape sequence, which may be followed by `a`, `b`, `f`, `n`, `r`, `t`, `v` or `\`. Specific characters can be provided using octal (`\nnn`) or hexadecimal (`\xnn`, `\unnnn` and `\Unnnnnnnn`) notations.

Conversely, escape characters are not parsed in string literals designated by backticks. It is important to note that, unlike Go, Prometheus does not discard newlines inside backticks.

Example:

```
"this is a string"
'these are unescaped: \n \\ \t'
`these are not unescaped: \n ' " \t`
```

### Float literals and time durations[](https://prometheus.io/docs/prometheus/latest/querying/basics/#float-literals-and-time-durations)

Scalar float values can be written as literal integer or floating-point numbers in the format (whitespace only included for better readability):

```
[-+]?(
      [0-9]*\.?[0-9]+([eE][-+]?[0-9]+)?
    | 0[xX][0-9a-fA-F]+
    | [nN][aA][nN]
    | [iI][nN][fF]
)
```

Examples:

```
23
-2.43
3.4e-9
0x8f
-Inf
NaN
```

Additionally, underscores (`_`) can be used in between decimal or hexadecimal digits to improve readability.

Examples:

```
1_000_000
.123_456_789
0x_53_AB_F3_82
```

Float literals are also used to specify durations in seconds. For convenience, decimal integer numbers may be combined with the following time units:

- `ms` – milliseconds
- `s` – seconds – 1s equals 1000ms
- `m` – minutes – 1m equals 60s (ignoring leap seconds)
- `h` – hours – 1h equals 60m
- `d` – days – 1d equals 24h (ignoring so-called daylight saving time)
- `w` – weeks – 1w equals 7d
- `y` – years – 1y equals 365d (ignoring leap days)

Suffixing a decimal integer number with one of the units above is a different representation of the equivalent number of seconds as a bare float literal.

Examples:

```
1s # Equivalent to 1.
2m # Equivalent to 120.
1ms # Equivalent to 0.001.
-2h # Equivalent to -7200.
```

The following examples do *not* work:

```
0xABm # No suffixing of hexadecimal numbers.
1.5h # Time units cannot be combined with a floating point.
+Infd # No suffixing of ±Inf or NaN.
```

Multiple units can be combined by concatenation of suffixed integers. Units must be ordered from the longest to the shortest. A given unit must only appear once per float literal.

Examples:

```
1h30m # Equivalent to 5400s and thus 5400.
12h34m56s # Equivalent to 45296s and thus 45296.
54s321ms # Equivalent to 54.321.
```

### Duration expressions[](https://prometheus.io/docs/prometheus/latest/querying/basics/#duration-expressions)

Arithmetic expressions can be used wherever a time duration is expected, that is in [range vector selectors](https://prometheus.io/docs/prometheus/latest/querying/basics/#range-vector-selectors) and in [offset durations](https://prometheus.io/docs/prometheus/latest/querying/basics/#offset-modifier).

In range vectors:

```
rate(http_requests_total[5m * 2])     # 10 minute range
rate(http_requests_total[(5+2) * 1m]) # 7 minute range
```

In offset durations:

```
http_requests_total offset (1h / 2)       # 30 minute offset
http_requests_total offset ((2 ^ 3) * 1m) # 8 minute offset
```

When using `offset` with a duration expression, you must wrap the expression in parentheses. Without parentheses, only the first duration value is used in the offset calculation.

The following operators are supported, following the usual precedence rules:

- `+` – addition
- `-` – subtraction
- `*` – multiplication
- `/` – division
- `%` – modulo
- `^` – exponentiation

The following functions can be used inside duration expressions:

- `step()` resolves to the step width of a [range query](https://prometheus.io/docs/prometheus/latest/querying/api/#range-queries), and to `0s` for an [instant query](https://prometheus.io/docs/prometheus/latest/querying/api/#instant-queries).
- `range()` resolves to the full range of a range query (end time − start time), and to `0s` for an instant query. This is particularly useful in combination with `@ end()` to look back over the entire query range, e.g. `max_over_time(metric[range()] @ end())`.
- `min_of(<duration>, <duration>)` returns the smaller of the two durations, which is useful for capping a duration at a maximum value.
- `max_of(<duration>, <duration>)` returns the larger of the two durations, which is useful for enforcing a minimum value.

For example, `max_of(step(), 5s)` ensures the duration is never shorter than `5s`, while `min_of(range(), 1h)` caps the duration at `1h`.

Note: Duration expressions are not supported in the [`@` modifier](https://prometheus.io/docs/prometheus/latest/querying/basics/#modifier).

Examples of equivalent durations:

- `5m * 2` is equivalent to `10m` or `600s`.
- `10m - 1m` is equivalent to `9m` or `540s`.
- `(5+2) * 1m` is equivalent to `7m` or `420s`.
- `1h / 2` is equivalent to `30m` or `1800s`.
- `4h % 3h` is equivalent to `1h` or `3600s`.
- `(2 ^ 3) * 1m` is equivalent to `8m` or `480s`.
- `step() + 1` is equivalent to the query step width increased by `1s`.
- `max_of(step(), 5s)` is equivalent to the larger of the query step width and `5s`.
- `min_of(2 * step() + 5s, 5m)` is equivalent to the smaller of twice the query step increased by `5s` and `5m`.

## Time series selectors[](https://prometheus.io/docs/prometheus/latest/querying/basics/#time-series-selectors)

These are the basic building-blocks that instruct PromQL what data to fetch.

### Instant vector selectors[](https://prometheus.io/docs/prometheus/latest/querying/basics/#instant-vector-selectors)

Instant vector selectors allow the selection of a set of time series and a single sample value for each at a given timestamp (point in time). In the simplest form, only a metric name is specified, which results in an instant vector containing elements for all time series that have this metric name.

The value returned will be that of the most recent sample at or before the query's evaluation timestamp (in the case of an [instant query](https://prometheus.io/docs/prometheus/latest/querying/api/#instant-queries)) or the current step within the query (in the case of a [range query](https://prometheus.io/docs/prometheus/latest/querying/api/#range-queries)). The [`@` modifier](https://prometheus.io/docs/prometheus/latest/querying/basics/#modifier) allows overriding the timestamp relative to which the selection takes place. Time series are only returned if their most recent sample is less than the [lookback period](https://prometheus.io/docs/prometheus/latest/querying/basics/#staleness) ago.

This example selects all time series that have the `http_requests_total` metric name, returning the most recent sample for each:

```
http_requests_total
```

It is possible to filter these time series further by appending a comma-separated list of label matchers in curly braces (`{}`).

This example selects only those time series with the `http_requests_total` metric name that also have the `job` label set to `prometheus` and their `group` label set to `canary`:

```
http_requests_total{job="prometheus",group="canary"}
```

It is also possible to negatively match a label value, or to match label values against regular expressions. The following label matching operators exist:

- `=`: Select labels that are exactly equal to the provided string.
- `!=`: Select labels that are not equal to the provided string.
- `=~`: Select labels that regex-match the provided string.
- `!~`: Select labels that do not regex-match the provided string.

[Regex](https://prometheus.io/docs/prometheus/latest/querying/basics/#regular-expressions) matches are fully anchored. A match of `env=~"foo"` is treated as `env=~"^foo$"`.

For example, this selects all `http_requests_total` time series for `staging`, `testing`, and `development` environments and HTTP methods other than `GET`.

```
http_requests_total{environment=~"staging|testing|development",method!="GET"}
```

Label matchers that match empty label values also select all time series that do not have the specific label set at all. It is possible to have multiple matchers for the same label name.

For example, given the dataset:

```
http_requests_total
http_requests_total{replica="rep-a"}
http_requests_total{replica="rep-b"}
http_requests_total{environment="development"}
```

The query `http_requests_total{environment=""}` would match and return:

```
http_requests_total
http_requests_total{replica="rep-a"}
http_requests_total{replica="rep-b"}
```

and would exclude:

```
http_requests_total{environment="development"}
```

Multiple matchers can be used for the same label name; they all must pass for a result to be returned.

The query:

```
http_requests_total{replica!="rep-a",replica=~"rep.*"}
```

Would then match:

```
http_requests_total{replica="rep-b"}
```

Vector selectors must either specify a name or at least one label matcher that does not match the empty string. The following expression is illegal:

```
{job=~".*"} # Bad!
```

In contrast, these expressions are valid as they both have a selector that does not match empty label values.

```
{job=~".+"}              # Good!
{job=~".*",method="get"} # Good!
```

Label matchers can also be applied to metric names by matching against the internal `__name__` label. For example, the expression `http_requests_total` is equivalent to `{__name__="http_requests_total"}`. Matchers other than `=` (`!=`, `=~`, `!~`) may also be used. The following expression selects all metrics that have a name starting with `job:`:

```
{__name__=~"job:.*"}
```

The metric name must not be one of the keywords `bool`, `on`, `ignoring`, `group_left` and `group_right`. The following expression is illegal:

```
on{} # Bad!
```

A workaround for this restriction is to use the `__name__` label:

```
{__name__="on"} # Good!
```

### Range Vector Selectors[](https://prometheus.io/docs/prometheus/latest/querying/basics/#range-vector-selectors)

Range vector literals work like instant vector literals, except that they select a range of samples back from the current instant. Syntactically, a [float literal](https://prometheus.io/docs/prometheus/latest/querying/basics/#float-literals-and-time-durations) is appended in square brackets (`[]`) at the end of a vector selector to specify for how many seconds back in time values should be fetched for each resulting range vector element. Commonly, the float literal uses the syntax with one or more time units, e.g. `[5m]`. The range is a left-open and right-closed interval, i.e. samples with timestamps coinciding with the left boundary of the range are excluded from the selection, while samples coinciding with the right boundary of the range are included in the selection.

In this example, we select all the values recorded less than 5m ago for all time series that have the metric name `http_requests_total` and a `job` label set to `prometheus`:

```
http_requests_total{job="prometheus"}[5m]
```

### Offset modifier[](https://prometheus.io/docs/prometheus/latest/querying/basics/#offset-modifier)

The `offset` modifier allows changing the time offset for individual instant and range vectors in a query.

For example, the following expression returns the value of `http_requests_total` 5 minutes in the past relative to the current query evaluation time:

```
http_requests_total offset 5m
```

Note that the `offset` modifier always needs to follow the selector immediately, i.e. the following would be correct:

```
sum(http_requests_total{method="GET"} offset 5m) // GOOD.
```

While the following would be *incorrect*:

```
sum(http_requests_total{method="GET"}) offset 5m // INVALID.
```

The same works for range vectors. This returns the 5-minute [rate](https://prometheus.io/docs/prometheus/latest/querying/functions/#rate) that `http_requests_total` had a week ago:

```
rate(http_requests_total[5m] offset 1w)
```

When querying for samples in the past, a negative offset will enable temporal comparisons forward in time:

```
rate(http_requests_total[5m] offset -1w)
```

Note that this allows a query to look ahead of its evaluation time.

### @ modifier[](https://prometheus.io/docs/prometheus/latest/querying/basics/#-modifier)

The `@` modifier allows changing the evaluation time for individual instant and range vectors in a query. The time supplied to the `@` modifier is a Unix timestamp and described with a float literal.

For example, the following expression returns the value of `http_requests_total` at `2021-01-04T07:40:00+00:00`:

```
http_requests_total @ 1609746000
```

Note that the `@` modifier always needs to follow the selector immediately, i.e. the following would be correct:

```
sum(http_requests_total{method="GET"} @ 1609746000) // GOOD.
```

While the following would be *incorrect*:

```
sum(http_requests_total{method="GET"}) @ 1609746000 // INVALID.
```

The same works for range vectors. This returns the 5-minute rate that `http_requests_total` had at `2021-01-04T07:40:00+00:00`:

```
rate(http_requests_total[5m] @ 1609746000)
```

The `@` modifier supports all representations of numeric literals described above. It works with the `offset` modifier where the offset is applied relative to the `@` modifier time. The results are the same irrespective of the order of the modifiers.

For example, these two queries will produce the same result:

```
# offset after @
http_requests_total @ 1609746000 offset 5m
# offset before @
http_requests_total offset 5m @ 1609746000
```

Additionally, `start()` and `end()` can also be used as values for the `@` modifier as special values.

For a range query, they resolve to the start and end of the range query respectively and remain the same for all steps.

For an instant query, `start()` and `end()` both resolve to the evaluation time.

```
http_requests_total @ start()
rate(http_requests_total[5m] @ end())
```

Note that the `@` modifier allows a query to look ahead of its evaluation time.

## Subquery[](https://prometheus.io/docs/prometheus/latest/querying/basics/#subquery)

Subquery allows you to run an instant query for a given range and resolution. The result of a subquery is a range vector.

Syntax: `<instant_query> '[' <range> ':' [<resolution>] ']' [ @ <float_literal> ] [ offset <float_literal> ]`

- `<resolution>` is optional. Default is the global evaluation interval.

## Gotchas[](https://prometheus.io/docs/prometheus/latest/querying/basics/#gotchas)

### Staleness[](https://prometheus.io/docs/prometheus/latest/querying/basics/#staleness)

The timestamps at which to sample data, during a query, are selected independently of the actual present time series data. This is mainly to support cases like aggregation (`sum`, `avg`, and so on), where multiple aggregated time series do not precisely align in time. Because of their independence, Prometheus needs to assign a value at those timestamps for each relevant time series. It does so by taking the newest sample that is less than the lookback period ago. The lookback period is 5 minutes by default, but can be [set with the `--query.lookback-delta` flag](https://prometheus.io/docs/prometheus/latest/command-line/prometheus/) or overridden on an individual query via the `lookback_delta` parameter.

If a target scrape or rule evaluation no longer returns a sample for a time series that was previously present, this time series will be marked as stale. If a target is removed, the previously retrieved time series will be marked as stale soon after removal.

If a query is evaluated at a sampling timestamp after a time series is marked as stale, then no value is returned for that time series. If new samples are subsequently ingested for that time series, they will be returned as expected.

A time series will go stale when it is no longer exported, or the target no longer exists. Such time series will disappear from graphs at the times of their latest collected sample, and they will not be returned in queries after they are marked stale.

Some exporters, which put their own timestamps on samples, get a different behaviour: series that stop being exported take the last value for (by default) 5 minutes before disappearing. The `track_timestamps_staleness` setting can change this.

### Avoiding slow queries and overloads[](https://prometheus.io/docs/prometheus/latest/querying/basics/#avoiding-slow-queries-and-overloads)

If a query needs to operate on a substantial amount of data, graphing it might time out or overload the server or browser. Thus, when constructing queries over unknown data, always start building the query in the tabular view of Prometheus's expression browser until the result set seems reasonable (hundreds, not thousands, of time series at most). Only when you have filtered or aggregated your data sufficiently, switch to graph mode. If the expression still takes too long to graph ad-hoc, pre-record it via a [recording rule](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/#recording-rules).

This is especially relevant for Prometheus's query language, where a bare metric name selector like `api_http_requests_total` could expand to thousands of time series with different labels. Also, keep in mind that expressions that aggregate over many time series will generate load on the server even if the output is only a small number of time series. This is similar to how it would be slow to sum all values of a column in a relational database, even if the output value is only a single number.
